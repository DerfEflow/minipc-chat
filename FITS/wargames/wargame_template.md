- Calibration (TruAgent payment schedule, 2026-08-05): **a migration's tests must cover the first
  ACTION taken after migrating, not just the shape of the migrated data.** Migrated records carry
  forward links that new records create differently, so an idempotency guard written for the new
  shape can miss the old one entirely. Here a migrated draw kept its original invoice id but had no
  `schedule_item_id`, so the scan-based double-bill guard missed it and the first button press would
  have billed every historic job a second time. The migration's own tests were green throughout —
  they checked the reshaped data and stopped there. Standing probe: after any migration, write one
  test that performs the most common next user action against a migrated record.
- Calibration (TruAgent payment schedule, 2026-08-05): **read the storage layer's concurrency model

  from reading the persistence diff code, not the spec. Where writers last-write-wins on a whole
  record, an in-record idempotency flag is not a guard; the guard has to live in a different record
  set than the one that can be lost.
