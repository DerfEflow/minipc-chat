PART 5. THE VARIABLES USED TO SORT THAT LIST
--------------------------------------------------------------------------------

These are the criteria, in the order they were applied. Change any of them and
the shortlist changes.

V1. REDUNDANCY AGAINST A DIRECT PROVIDER          weight: hard exclude
    Your stated rule. If Dominion already reaches the model through that vendor's
    own API, the NVIDIA copy is dropped. Removed Kimi and both DeepSeeks.

V2. GENERATION CURRENCY                            weight: hard exclude
    If a newer model from the same family is on the same endpoint, the older one
    goes. This is what emptied group J. It is a judgment about naming and version
    numbers, not about measured quality.

V3. PICKER HYGIENE                                 weight: high
    A curated dozen beats a wall of 102. A user scrolling a long list of
    near-identical names picks worse, not better. This is the reason the
    shortlist is short rather than generous.

V4. CAPABILITY DOMINION DOES NOT ALREADY HAVE      weight: high
    Ranked a model up if it does something the current catalog cannot: document
    parsing, spatial reasoning, free embeddings, guarding.

V5. COST                                           weight: high
    Free or near-free only, which is your framing. NOT VERIFIED per model. The
    model list does not report pricing.

V6. ARCHITECTURAL AND VENDOR DIVERSITY             weight: medium
    Preferred one strong model from several labs over several from one lab. A
    catalog of six Nemotrons fails differently than a catalog of six labs, and
    correlated failure across a whole lane is worse than any single weak model.

V7. NAME RECOGNITION                               weight: medium
    A user picking a model reads the name. "gpt-oss" and "Gemma" carry meaning to
    people who have never heard of Nemotron. This is a product criterion, not a
    technical one.

V8. ADJACENCY TO YOUR OTHER WORK                   weight: medium
    Ranked up where a model touches something you already do: creative writing,
    spatial reasoning for aerial measurement, code embeddings.

V9. PRIOR INCIDENT HISTORY                         weight: flag, not exclude
    MiniMax stays on the list with its 2026-07-12 failure attached rather than
    being silently dropped.


WHAT WAS NOT USED, BECAUSE THE DATA DOES NOT EXIST YET
--------------------------------------------------------------------------------

None of the following were available, and all of them outrank everything in
Part 5. Any of them could overturn the shortlist entirely.

  - TOOL CALLING. Whether a model emits a real tool call or merely describes one.
    For build and IDE work this is pass or fail, and it is unknown for every
    model above. A model that cannot call a tool is useless to the Crucible no
    matter how good it reads.

  - REAL CONTEXT WINDOW. Not in the list response.

  - PROVIDER OUTPUT CEILING per request, and whether reasoning tokens consume it.

  - RATE LIMITS on your developer tier. You report them as far beyond current
    need. Phase A records the actual figures.

  - FREE VERSUS BILLED status per model on your tier.

  - IMAGE SUPPORT, confirmed rather than inferred from a name containing "vl" or
    "vision".

  - MEASURED QUALITY. No benchmark was consulted and none is claimed. Every
    quality-flavoured word in Part 4 is a guess about a model's role, not a
    finding about its ability.

fleet_probe.mjs already answers three of these (does it answer, does it emit a
real tool call, does it accept an image) for NVIDIA and Moonshot. Phase A extends
it to the full shortlist and adds the output-ceiling and reasoning-budget checks.
